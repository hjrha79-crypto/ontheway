## STEP 1. P0-0 진단 지시문 (Claude Code에 바로 붙여넣기)

```
OnTheWay v3.19 P0-0 긴급 작업: 시간 데이터 오염 수정

[배경]
2026-04-20 21:45 발견.
현재 시각 21:45인데 이벤트 타임스탬프가 22:54, 22:27, 22:06, 
21:59, 21:58, 21:52로 기록됨. 21:42:51만 유일하게 실제 감지 시각.

[유력 가설]
배민 앱 화면의 "도착예정시간"/"도착예상시간" 미래 시각 텍스트를
OnTheWay 파서가 콜 감지 시각으로 오인 파싱.
사례 1~4 가게명 오파싱과 동일한 뿌리 문제.

[치명적 영향]
- 세션 TTL(30초) 판단 불가
- suppressionList TTL 무력화 → P0-1 효과 없을 가능성
- event_id time_bucket_10s 계산 오류
- MoneyMap/시급 계산 난수 수준

[1단계: 현황 파악] - 코드 수정 금지, 분석만

A. 콜 감지 시각 생성 지점 추적
   - CallSession 및 MobilityEvent의 시각 관련 필드 모두 나열
     (detectedAt, timestamp, createdAt, startTime 등)
   - 각 필드가 어디서 어떻게 할당되는지 코드 인용
   - System.currentTimeMillis() 직접 사용인가?
   - 아니면 파서가 추출한 텍스트에서 파싱한 값인가?

B. BaeminParser 시간 텍스트 추출 여부
   - "도착예정시간", "도착예상시간", "예상시간" 등 한글 키워드
     검색해서 해당 로직 인용
   - HH:MM 정규식 패턴 매칭 코드 전수 확인
   - 추출된 시각이 어느 필드에 저장되는가?

C. StateTransitionLog 타임스탬프
   - 로그 기록 시각도 오염됐는가?
   - adb logcat 출력 시각 vs DB 기록 시각 비교
   - 로그 기록이 정상이면 표시 로직만 오염
   - 로그 기록도 오염이면 생성 단계부터 오염

D. UI 표시 로직 확인
   - 메인 화면 리스트의 "21:42:51" 형식 시각 표시가
     어느 필드를 읽어서 어떻게 포맷팅하는가?
   - SimpleDateFormat 사용 시 TimeZone 설정 확인

E. 유닛테스트의 시간 처리 확인
   - 테스트 케이스가 시간을 어떻게 주입하는가?
   - 하드코딩 값이면 현실 검증 불가능했음
   - 이게 P0-1 유닛테스트 88개 통과한 이유일 수도 있음

[보고 형식]
각 항목마다:
- 발견된 코드 (파일:라인 인용)
- 현재 동작 설명
- 오염 가능성 평가 (높음/중간/낮음 + 근거)

추측 금지. 코드 근거로만 답변.

1단계 보고 후 사용자 승인 받고 2단계(수정 방향 확정) 진행.

[원칙]
- 현상 → 원인 추적 → 구조 수정 → 코드 수정
- 유닛테스트 통과 = 완료 아님
- 사용자 명시 지시 없이 기능 추가 절대 금지
- 각 단계 완료 시 보고 후 승인
```

## STEP 2. 진단 검토 체크포인트

Claude Code의 1단계 보고를 받은 후 제(외부 Claude)가 검토할 항목:

```
[필수 확인]
☐ detectedAt 필드가 System.currentTimeMillis() 기반인지
☐ BaeminParser가 "도착예정시간" 텍스트를 어디에 쓰는지
☐ 해당 텍스트가 세션 타임스탬프로 흘러들어가는 경로가 있는지

[판단 기준]
Case A: 파서가 화면 시각 텍스트를 detectedAt에 넣고 있음
        → 원인 확정, 수정 방향 명확 → STEP 3 진행

Case B: detectedAt은 System.currentTimeMillis() 기반
        → 원인 다른 곳에 있음 → 추가 진단 필요 → 
          재진단 지시문 만들어서 오늘 밤 내로 끝낼 수 있는지 판단.
          어려우면 원인 파악까지만 하고 내일 수정.

Case C: 표시 로직(UI)만 오염, 데이터는 정상
        → 수정 간단, TimeZone 보정 1줄 → STEP 3 진행

[금지]
- Case B인데 억지로 STEP 3 진행 (잘못된 수정 → 새 버그)
- "일단 수정하고 보자" 식 접근
```

## STEP 3. 수정 구현 지시문 (Case A 기준 템플릿)

```
P0-0 2단계: 시간 데이터 오염 수정 구현

[수정 원칙]
1. detectedAt(콜 감지 시각)은 무조건 System.currentTimeMillis() 기반
2. 배민 화면의 "도착예정시간" 등은 파싱하되 별도 필드에 저장
   (예: expectedArrivalTime - 새 필드 추가 가능)
3. 미래 시각 방어 로직:
   - detectedAt > now() + 5초 감지 시 warn 로그 + now()로 보정
   - StateTransitionLog에 "FutureTimestampCorrected" 태그 기록
4. 기존 오염 데이터 정리:
   - DB에서 detectedAt > now() + 5초인 레코드 식별 쿼리 작성
   - 실행은 하지 말고 SQL만 제공 (사용자가 검토 후 결정)

[작업 순서]
1. 수정 파일 목록 제시 (승인 받고 진행)
2. 코드 수정
3. 유닛테스트 추가:
   - 미래 시각 주입 시 now()로 보정되는지
   - 정상 시각은 그대로 유지되는지
   - 배민 "도착예정시간" 텍스트 무시되는지
4. 기존 유닛테스트 88개 전부 통과 확인
5. APK 빌드
6. 변경 요약 보고

[금지]
- 수정 범위 확장 금지 (가게명 오파싱 같이 고치려 하지 말 것)
- 새 기능 추가 금지
- 유닛테스트 실패 시 억지 통과 금지 (즉시 보고)

[완료 기준]
- 유닛테스트 전체 통과
- APK 빌드 성공
- 오염 데이터 식별 SQL 제시 완료
```

## STEP 4. 빌드 + 설치 + 실전 검증

```
1. APK 빌드 성공 확인
2. 기존 앱 삭제 (중요)
3. 새 APK 설치
4. 바로 OnTheWay 홈 화면 열기
5. 현재 시각 확인 (예: 22:30)
6. 기존 이벤트 리스트 삭제 or 새로 콜 1~2건 대기
7. 새로 들어오는 콜의 "감지 시각"이 현재 시각과 일치하는지 확인
   - ✅ 일치 → P0-0 성공
   - ❌ 미래 시각 여전 → 원인 다른 곳, 오늘 밤 여기까지 / 내일 재진단

[주의]
- 실전 검증 안 끝나면 P0-1 재검증으로 넘어가지 말 것
- 새 콜 안 오면 실전 검증 스킵하고 오늘 마감
```

```

- 원인 파악만 해도 충분한 진전
- 구현은 내일 맑은 머리로 해도 늦지 않음
```
